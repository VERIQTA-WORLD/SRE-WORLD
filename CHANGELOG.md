# Changelog

All notable changes to SRE World will be documented in this file.

SRE World uses [Semantic Versioning](https://semver.org/) for repository releases and follows the structure of [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## Versioning

```text
MAJOR.MINOR.PATCH
```

- `MAJOR` indicates a substantial change to the repository structure, standards, or learning model that may break existing links or contribution workflows.
- `MINOR` indicates a new knowledge section, collection, learning path, template family, or significant body of backward-compatible content.
- `PATCH` indicates corrections, link repairs, metadata updates, small content improvements, and other backward-compatible maintenance.

The `Unreleased` section records accepted changes that have not yet been assigned to a release.

## Resource Change Format

Use this format when adding or changing an individual resource:

```text
- Added `[RESOURCE-ID] Resource Title` to `Repository/Path`.
- Updated `[RESOURCE-ID] Resource Title` with a new canonical link.
- Marked `[RESOURCE-ID] Resource Title` as Archived.
- Superseded `[OLD-ID] Old Resource` with `[NEW-ID] New Resource`.
- Removed `[RESOURCE-ID] Resource Title` because [reason].
```

Examples:

```text
- Added `SRE-SLO-BOOK-001` to `03-SLIs-SLOs-and-SLAs`.
- Fixed the canonical link for `SRE-INC-POST-004`.
- Marked `SRE-OBS-TOOL-002` as Archived after upstream maintenance ended.
- Removed `SRE-ALT-ARTICLE-009` because it duplicated an authoritative source.
```

Do not reuse a retired resource ID.

## Release Checklist

Before publishing a release:

- [ ] Move completed entries from `Unreleased` into the new version.
- [ ] Use the release date in `YYYY-MM-DD` format.
- [ ] Confirm that every listed change exists in the repository.
- [ ] Confirm that internal links work.
- [ ] Record new, changed, fixed, removed, deprecated, and security-related items.
- [ ] Identify retired or superseded resource IDs.
- [ ] Avoid listing planned work as completed work.
- [ ] Keep empty categories only when consistency is useful.
- [ ] Update the repository version or release tag where applicable.
- [ ] Review the rendered Markdown before release.
